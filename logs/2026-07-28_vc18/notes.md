# `v_cruise` 정식값 18.0 — 실측 기록

**코드 로직은 한 줄도 바꾸지 않았다.** 바뀐 것은 ①yaml `v_cruise` 20.0 → **18.0**(+ 정식 근거 주석)
②`planner_eta_s()` 의 코너당 어림값 75s → **90s**(예고가 실측을 밑돌 뻔했다) ③측정 도구 2건 신설이다.

- 실행 환경: WSL `Ubuntu-22.04`, `gz_standard_vtol`, PX4 `/root/PX4-vehicle`(`c890d9db0a`)
- 시나리오 사이 `wsl.exe --terminate Ubuntu-22.04` 전건 적용
- 시나리오 정의 **무수정** — 기존 `R2_*` 를 그대로 쓰고 `--run-id <id>_vc18` 로만 구분했다.
  `v_cruise` 는 launch 인자가 아니라 **yaml 정식값 18.0** 으로 들어갔다(= 배포될 값 그대로 검증).
- 원본: `<run>/node.log` · `meta.json` · `metrics.json` · `verdict.md`.

## 4. 폐곡선 `d_end_thresh` 여유 재측정 (R2 인계사항)

R2 가 남긴 경고: `R2_closed` 는 FOLLOWING 진입 시 종점까지 13.3m 뿐이고 `d_end_thresh` 10m 와
여유가 3.3m — `v_cruise` 를 바꾸면 더 줄 수 있다. **재측정했다.**

`node.log` 의 `FOLLOWING 시작 pos=[N,E]`, 폐회로에서 종점 = 원점 = 시작점.

**측정값: 폐회로 여유 4.00m → 2.18m 로 줄었다.**

**그러나 원인은 `v_cruise` 가 아니다 — 이게 더 나쁜 소식이다.**

누적 타이밍이 정하는 **런간 변동량**이고, 관측대역은 **10.60~15.32m** 다.

⇒ **완전 폐회로에서 `d_end_thresh` 10.0m 대비 실제 최악 여유는 0.6m 다.**
   R2 가 "3.3m 뿐"이라 경고한 것보다 **더 얇다.** 여유가 0 이하가 되면
   `trans_mc_trigger` 가 **출발하자마자 "경로 완료"** 로 판정해 한 바퀴를 통째로 건너뛴다.
   이번 5런에서는 발현하지 않았지만(전 런 완주), **R5 의 `d_end_thresh` 작업은 이 시나리오를
   반드시 함께 돌려야 하고, 값을 키우는 방향(오버슈트 0 → ≈57)은 폐회로를 즉시 깬다.**
   (범위 밖이라 이번엔 값을 건드리지 않았다.)
