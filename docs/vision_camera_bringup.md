### 이번 세션에 실기에서 잡은 것들 (재개 전 반드시 인지)

- **🔴 LensPosition ≠ 1/거리. 약 2배 어긋난다.** 보드 0.5m에서 스윕 피크가 L=2.0이 아니라
  **L=4.0**(선명도 57.1 vs 이웃 20.7/22.1 — 또렷한 피크라 의심의 여지 없음). 촬영 세션의
  명시적 검정 항목이었고, **답은 "가정 틀림"**이다. 클론 VCM 눈금이 진짜 디옵터의 ~2배.
  **계획은 안 깨진다** — 외삽은 L이 진짜 디옵터와 *선형*이기만 하면 되고,
  `fx(L)=fx_inf·(1+(f/k)·L)`로 여전히 L=0이 무한대다. 영향은 두 가지뿐:
  `b/a` 초점거리 검사가 f 대신 f/k(≈2.4mm)를 뱉고(허용범위 안이라 통과), 디옵터 검사는
  ~100% 오차로 **실패하는 게 정답**이다.
- **🔴 재잠금 금지 — 거리당 딱 한 번, 보드 정면·정중앙에서.** 잠금은 *그 샷의 타겟존* 안에서
  선명도를 재므로, 존이 u=0.2/0.8로 옮겨가고 보드가 기울면 다른 L로 수렴한다(실기: 정면
  3장 L=4.0, 요잉 ±30° 2장 L=3.0). L은 이 분석의 핵심 축이라 **거리당 하나여야 한다.**
  `calib_analyze.group_lens_position_spread()`가 이 섞임을 감지하도록 추가해뒀다(검사 배선 미완).
- **🔴 자동촬영 "끄기" 버튼이 오히려 켰다 — 수정 완료(커밋 `7666e79`).** GET 폼이 action의
  쿼리스트링을 버리는 HTML 사양 때문. **재개 시 라파의 `calib_capture.py`를 꼭 갱신할 것**
  (위 재개 절차의 `git checkout` 줄). 갱신 전에는 주소창에 직접
  `http://<IP>:8081/autocapture?enabled=0`을 쳐야 꺼진다.
- **카메라가 상하반전 마운트돼 있다**(고정 문제). 광축 180° 회전이라 **좌우도 같이 뒤집힌다** —
  조준 시 한글 라벨("상단"/"좌측") 무시하고 **화면의 노란 박스만** 따를 것.
  인트린식 영향: fx·fy·k1·k2·k3 무영향 / cx,cy는 그 방향 기준으로 정확(정립 마운트로 바꾸면
  `W-cx, H-cy`) / p1,p2 부호 반전. 아티팩트에 `image_orientation` 기록하는 것 **미구현**.
- **조도 실측:** 보드 위치에서 **60 lux**(카메라 시야 방향으로 재면 창문 때문에 400 lux로
  뻥튀기됨 — 보드에 떨어지는 빛을 재야 한다). 60 lux면 f/1.8에서 필요 노출 118ms이고
  실측이 50ms@게인2.0(=100ms 상당)이라 **렌즈는 정상**이다. 다만 어두우니 조명을 더 주면
  게인 노이즈가 준다.
- **sharpness 변동의 원인은 특정 못 했다.** 볼트 고정 + 동일 렌즈/노출/게인인데도 52.9/40.3/64.4
  (자세만 다름). 기울기 단조성도 안 보인다(정면 52.9 < 피칭35° 64.4). **표본 5개로는 무리** —
  그리고 **신경 쓸 필요 없다.** 이건 블러 게이트용 휴리스틱일 뿐이고, 촬영본의 실제 품질은
  분석기의 **사진별 재투영오차**가 훨씬 정확하게 판정한다. 게이트(기준의 40%)는 넉넉하다.

### 🆕 촬영 흐름 결함 진단 + 수정 계획 (2026-07-23, WSL 로컬 세션 — 라파 미연결, 코드+회수데이터 분석만)

사용자 보고: "자동촬영 간격이 너무 빨라 뭘 해볼 틈도 없이 슉슉 넘어간다" + "sharpness 한계 때문에
안 흔들린 사진도 흔들렸다고 오판해 대량 거부됐다(거부분은 저장 안 돼 데이터에 안 남으므로
이전 세션이 '잘 찍힌 사진들'만 보고 로직 문제없다고 한 건 생존자 편향)". 라파 미연결이라
실기 재현은 못 했지만, 코드 정독 + 위 "이번 세션에 실기에서 잡은 것들"의 회수 사이드카 JSON
(`vision/data/calibration_raw/2026-07-23_session1/A/0.5m/00{1..5}.json`)을 직접 계산해
교차검증했다. **둘 다 실재하는 결함이고 원인을 코드 레벨로 특정했다.**

**결함 A — 자동촬영 상태가 샷 전환 시 초기화 안 됨(`calib_capture.py`):**
`_capture_locked()`(951~1027행)가 촬영 성공 후 `shot_idx`는 전진시키지만
`corner_history`/`autocapture_pending_since`를 초기화하지 않는다(`skip()`/`prev()`도 동일).
`corners_are_stable()`은 "최근 5프레임이 서로 2px 미만"만 보므로, 방금 촬영이 성공했다는
사실 자체가 이미 "5프레임 연속 안정"이었다는 뜻 — 이 이력을 다음 샷이 그대로 물려받는다.
**연속 샷이 같은 (u,v) 존을 공유하면**(세트B는 그리드 위치당 틸트 3장이 같은 존, 세트A도
"정중앙" 존이 15장 중 4번 반복) 안정성 검사가 사실상 스킵되고 `in_zone`도 곧바로 참이 돼,
남는 건 `DEFAULT_AUTO_CAPTURE_DELAY_S=1.2초` 카운트다운뿐이다 — 사용자가 보드를 실제로
새 자세로 바꾸기도 전에 재촬영된다. 단순히 지연시간을 늘리는 걸로는 안 고쳐진다(안정성
게이트 자체가 우회되므로), **상태 초기화가 먼저다.**

**결함 B — 블러 판정 기준(`reference_sharpness`)과 샘플이 서로 다른 크롭 영역을 잼:**
`run_focus_sweep_and_lock()`(841~850행)의 `reference_sharpness`는 **명목 타겟존 박스**
(`zone_to_pixel_rect`, 공식 기반 고정 크기)로 크롭해서 재는데, `_capture_locked()`(975행)의
매 샷 `sharpness`는 **실제 검출된 코너 바운딩박스**(+15%마진, `board_region_sharpness`)로
잰다. 회수 데이터로 두 크롭 면적을 직접 비교(A/0.5m 정중앙 3장): 실제 보드 bbox+마진
1176×775px vs 명목 타겟존 1928×1350px — **타겟존이 2.86배 넓다**(배경까지 포함). 라플라시안
분산은 크롭 영역에 비불변이라 애초에 비교가 성립하지 않는다. 실측 근거: 샷1(정면·회전없음·
볼트고정·잠금 직후 촬영이라 사실상 동일 조건)조차 `sharpness=52.6` vs `reference=82.7` —
**비율 0.64**, 실제로 안 흔들렸는데 40% 손실로 보임. 샷5는 비율 0.499로 `blur_ratio=0.4`
문턱을 겨우 넘김 — 통과/거부가 사실상 운이다. **거부된 촬영은 이미지도 사유도 디스크에
전혀 안 남는다**(오버레이 텍스트만 잠깐 떴다 사라짐) — 이게 "생존자 편향" 지적의 근거.

**정정 — ffmpeg 관련 오해:** 세션 중 "ffmpeg 도입해서 60fps 아니냐"는 질문이 나왔는데
**틀린 전제다.** Phase 3(ffmpeg/H.264, 위 로드맵)은 아직 `▶ 다음 차례`로 시작도 안 했고,
지금 `calib_capture.py`가 쓰는 스트림은 여전히 `utils/stream.py`의 `MjpegStreamer`(cv2
JPEG인코딩+HTTP multipart, 순수 파이썬)다. 게다가 **"촬영 중 관측된 성능" 절(아래, 이미
실측 기록됨)에 답이 이미 있었다** — 세트A는 `findChessboardCorners` 실패 시 545ms가 걸려
실측 ~1.4fps(≈714ms/틱)로 코드 기본값 `--preview-interval 0.2`가 무의미해진 상태다. 사용자가
체감한 "1.5초"는 이 실측치와 같은 자릿수 — **결함 A의 안정성 판정이 "5프레임=1초치"를
가정하고 짠 로직인데 실제 틱 간격이 ~0.7초대(세트A)라 전제 자체가 어긋나 있었다는 뜻이고**,
carry-over 버그(결함 A)와 겹치면 사용자 입장에선 화면이 몇 번 갱신되기도 전에 이미 찍혀버리는
것처럼 보인다. 즉 이 성능 이슈는 원래 "촬영 완료 후 개선"으로 미뤄둔 항목이었지만, 결함 A의
UX 체감과 직접 얽혀 있으므로 재개 전 함께 처리하는 걸 권한다(검출을 N틱마다만 돌리거나
별도 스레드로 분리).

**수정 계획:**
- **0순위 — 계측 추가(선행 필수):** 거부된 촬영 시도도 사유+sharpness값+포즈를 JSONL로
  기록(이미지 저장은 선택). 이게 없으면 임계값 튜닝을 또 감으로 하게 됨 — 데이터 없이
  "이제 됐다" 판단 금지.
- **결함 A 수정:** `_capture_locked()`/`skip()`/`prev()` 세 곳에서 shot 전환 시
  `corner_history.clear()` + `autocapture_pending_since = None`을 호출하는 헬퍼 하나로 통일.
  `DEFAULT_AUTO_CAPTURE_DELAY_S`(1.2s)는 상태 초기화가 살아나면 재검토 — 무작정 늘리기 전에
  먼저 이 버그부터 고치고 실기로 체감 재평가.
- **결함 B 수정:** `run_focus_sweep_and_lock()`의 reference도 `_capture_locked()`와 동일한
  `board_region_sharpness()`(검출된 코너 bbox 기반)로 측정 — 크롭 정의 통일이 근본 수정.


**기본상태 캡처는 IPC를 안 타서 멀쩡하다.** 그래서 1d·2a 검증을 그대로 통과해버렸고,

- **release 빌드에서 연속 AF의 `Focused` 도달은 재확인 못 했다.** debug 빌드에선 확인됨
  (119프레임/6.04초에 lens 5.563 수렴, lapvar 2.02→4.90). release 검증 시점엔 장면 조도가
  178→91 Lux로 떨어지고 텍스처가 사라져 스윕 전체가 평평(피크비 1.3~1.4배)했고, AF는 피크
  구간(11.50)에 도달했으나 `Failed`를 반환했다 — 신뢰도 임계 미달로 **알고리즘적으로 올바른
  거동**이다. 렌즈 위치제어 자체는 0~15 전 구간 정확. **체커보드 촬영 때 텍스처 있는 장면에서
  재확인할 것.**
- ④ AF 윈도우: 두 윈도우 수렴값이 5.637 vs 5.570으로 0.067 차이 — 원격이라 사람이 물체를 다른
  거리에 못 놓아 깊이 분리 자체가 불가능했다. 메커니즘(윈도우별 독립 재스캔)은 확인됨.
  **현장에 사람이 있는 촬영 세션에서 자연히 해소된다.**

## 0. 왜 이 작업인가 (한 문단)

지난 6세션이 카메라를 **V4L2 raw 직접 캡처로 우회**해 브링업했으나, 그 결과 오토포커스·자동노출·자동화벨이 전무해 수동 스윕(거리당 수 분)·gray-world 수동보정·1.5초 슬라이드쇼로 귀결됐다. 근본원인은 하드웨어도 커널도 아니고 **딱 하나** — Ubuntu 24.04의 `libcamera-ipa` 패키지에 RPi5용 `ipa_rpi_pisp.so`가 빠져 있어 libcamera가 카메라를 0대로 본다. **이건 배포판 패키징 누락일 뿐이라 소스빌드로 살릴 수 있다.** libcamera가 살면 AF/AE/AWB(품질)와 연속 H.264 영상(스트리밍)이 **동시에** 풀리고, 우회책 814줄 + MJPEG + 200줄 포렌치 노트가 통째로 폐기된다.

## 1. 확정 전제 (재논의 불필요)

- **호스트 OS 유지(Ubuntu 24.04). 로컬 prefix 비파괴 빌드.** OS 이주 안 한다 — tailscale/docker/ros/wifi 완화조치/EEPROM 전원설정 전부 무손상, 원격으로 진행 가능. (OS 이주는 헤드리스 최초설정에 물리 키보드·모니터가 필요해 원격 관리와 충돌 → 후퇴선으로만 둔다.)
- **RPi5 카메라·영상·텔레메트리 물리 배치는 확정, 논의 대상 아님:**
  - 카메라(서드파티 IMX708 클론 CAM109) → 호스트 `/dev/video*`·`/dev/media*`
  - 영상 다운링크 → **RTL8812AU USB(호스트)**, 지상국과 통신 (아직 미장착, 목표 하드웨어)
  - MAVLink 텔레메트리 → **픽스호크에 직결된 별도 라디오** (RPi·도커 무관)
  - offboard 제어용 MAVROS → 컨테이너 `fc`(ros:humble), `/dev/ttyACM0`
- **컨테이너 `fc`는 `NET=host`** — 호스트↔컨테이너 네트워크 경계 없음. vision(호스트)→ROS2(컨테이너) 다리는 루프백 IPC 하나면 됨. **영상은 컨테이너를 지나지 않는다.**
- 소스 이미 준비됨: `/home/suri/local-libcamera-src/libcamera` (clone 완료, 빌드의존성 apt 설치 완료, `meson setup` 미실행). 상세는 메모리 `project_rpi5_ubuntu_camera_stack.md`.

## 2. Phase별 실행 (각 Phase 끝에 보고 게이트)

### Phase 1 — libcamera 부활 (핵심, 성패 결정) — ✅ **완료 2026-07-23** (아래는 당시 지시 원문)
- **1a.** `/home/suri/local-libcamera-src/libcamera`에서 meson 옵션에 pisp 파이프라인/IPA가 켜지는지 확인 후 `meson setup build --prefix=/home/suri/local-libcamera` (필요시 `-Dpipelines=rpi/pisp -Dipas=rpi/pisp`). **→ 여기까지만 하고 보고.**
- **1b.** `ninja -C build`. RPi5라 시간 걸릴 수 있으나 로컬 빌드라 네트워크 무관(과거 apt 지연은 네트워크 탓, 빌드엔 무관). **→ 보고.**
- **1c.** 산출물에 **`ipa_rpi_pisp.so` 존재 확인** — 나오면 사실상 승리.
- **1d.** 환경변수(`LIBCAMERA_IPA_MODULE_PATH`/`LD_LIBRARY_PATH`/`PYTHONPATH`)로 로컬 빌드를 가리켜 `CameraManager.singleton().cameras`가 **빈 리스트가 아닌지** 확인. **→ 보고.**
- ⚠️ **1d까지 실패 시 후퇴선:** Bookworm A/B SD카드(빈 카드 굽고 `rpicam-hello` 10분 판정). 이주 아님, "카메라 진짜 되나"만 확인. SD가 부트순서 1순위라(BOOT_ORDER=0xf461, 실측) 카드만 꽂으면 Bookworm 부팅, 빼면 기존 Ubuntu USB 복귀 — 기존 시스템 무손상.

### Phase 2 — picamera2로 6기능 실측 검증 — ✅ **완료 2026-07-23** (5 WORKS / 1 PARTIAL, 위 요약 참조)
libcamera 살면 picamera2 설치 후 각각 **직접 재현 검증**(pseudo 금지):
① 초점 목표값 1초내 반영 ② 진짜 연속 AF ③ AF↔MF 전환 ④ **AF 윈도우(영역) 지정** ⑤ AE 자동/수동 전환 ⑥ AWB 자동/수동 전환. 되면 지난 세션의 수동 스윕·gray-world·정착시간 조사가 전부 불필요해짐.

### Phase 3 — ffmpeg 영상 (디버깅 + 다운링크 통합) — ▶ **다음 차례**
- `rpicam-vid`/`libcamera-vid` → **연속 H.264** → 랩탑 `ffplay`/`mpv`(브라우저 아님, 저지연 UDP/RTSP). 이게 디버깅 주경로.
- **같은 H.264 인코드를 RTL8812AU 다운링크와 공유** — 계획서 §7.7 EncoderSink 스왑 어댑터가 원래 의도한 구조. 인코드 경로 하나로 디버깅+대회 다운링크 동시 충족.
- MJPEG-over-HTTP(`utils/stream.py`)는 이 시점에 폐기 후보로 전환.

### Phase 4 — 통합·폐기 (별건, 위 검증 후)
- `vision/utils/frame_source.py::LiveFrameSource`를 picamera2 백엔드로 재구현 — 계획서가 정한 정식 이음매(현재 `cv2.VideoCapture` 구현은 V4L2 raw 경로와 비호환, 실측됨).
- **격리 대상(= 우회책 대청소 본체):** `vision/tools/rpi_capture.py`의 V4L2 814줄(`unpack_raw10`/`debayer_to_bgr8`/gray-world/focus-sweep/media 동적탐색) + `vision/CLAUDE.md`의 관련 200줄 포렌식 노트. **libcamera 부활 전엔 아직 유효하므로 Phase 1 성공 전에는 건드리지 말 것.**
