## 1. 시스템 목적

RPi5 온보드에서 실행. 카메라(+1D 하향 라이다)로 착륙지점 객체를 인식 → **기체 기준 상대 위치/자세**를 산출 → 기체를 객체 수직 상공으로 유도 → 안전 착륙. **최종 정확도 <30cm.** 매 실행명령마다 수행하며, **타겟 종류는 명령(CC)이 지정**한다(버티포트 / 조난자 구역 / 하기구역 / 단순 착륙).

- 비행 고도: 약 20~40m에서 하강 시작. 객체 크기 약 0.2~3m.
- 요구 #1 RPi5에서 원활히 동작. #2 저품질이라도 지상에서 작동 장면 관측 가능. **#3 대회날 오작동·인식실패·오인식 절대 불가** — 최초 인식에 시간이 조금 걸려도(≤5s) **안전한(성공확률 높은) 방법 우선**.

  - 그 안쪽 **검은 V**는 실물도 검은색 인쇄 확인됨 — solid라 저해상에서도 강한 2차 형상 확인 신호로 유효.
  - **하기안전구역(빨간 원): 직경 2m, 선굵기 5cm — 채워진 disc가 아니라 5cm 두께의 얇은 고리(annulus).** 다만 이제는 흰 필드(채워짐)가 이미 1차 coarse 신호를 맡으므로, 빨간 고리는 **coarse 2차 확인/허용오차 경계** 역할이면 충분 — 색게이팅(HSV 빨강)으로 후보 픽셀만 추린 뒤 그 점들에 원 피팅(최소외접원/대수적 원피팅)으로 검증한다. 일반 그레이스케일 Hough보다 색으로 먼저 거르는 쪽이 클러터 오탐도 적고 계산도 가볍다(§5.2).
- **초록 색/치수(②):** **[2026-07-21 확정] 앞으로도 비공개 예정.** 버티포트와 비슷한 크기로 가정하되 **안전마진으로 약간 더 작게** 잡는다(coarse 매트 크기 가정에 반영, §5.3).

## 4. 물리적 제약 (설계의 척추)

### 4.1 GSD / 고도 vs 해상도

수평화각 102°, 지상폭 = 2·h·tan(51°) ≈ 2.47·h.

| 고도 | 네이티브(4608px) GSD | 다운스케일(1536px) GSD | 3m 피처(다운) | 50cm ArUco(네이티브 ROI) | 20cm 박스(네이티브) |
|---|---|---|---|---|---|
| 40m | 2.14 cm/px | 6.4 cm/px | 47px ✅ | 23px ✗ | 9px ✗ |
| 20m | 1.07 | 3.2 | 94px ✅ | 47px ✅ | 19px △ |
| 10m | 0.54 | 1.6 | — | 93px ✅ | 37px ✅ |

- **coarse**(3m 피처)는 **다운스케일 전체프레임**으로 40m부터 획득.
- **fine ArUco**는 **네이티브 해상 ROI 크롭**으로 디코드 → 신뢰 디코드(≈30~40px 이상) **~20m 이하**. 12MP 고해상 + ROI가 이걸 가능케 함. **[2026-07-21 §4.1a에서 실측 규격(50cm)으로 재확인 — 이 표 그대로 유효, 정정 없음]**
- 20cm 박스는 **~10~15m 이하**에서 검출.
- 결론: **2단 하강 강제.** fine 피처 락·검증 전엔 최종 착륙 커밋 금지.

### 4.1a ArUco 실측 규격 확인 (2026-07-21) — 원표 유효, 오인 정정 이력

세션 중 한때 마커 물리크기를 100mm(10cm)로 잘못 파악해 "50cm 가정과 5배 차이 → fine-lock 고도 ~20m→~5m로 축소"라는 경보를 냈으나, **사용자 확인 결과 오인이었다.** 첨부됐던 arucogen 스크린샷의 "Marker size: 100mm"는 웹 생성기의 임의 테스트값이었고, **실제 인쇄 규격은 버티포트 표준 파일(150dpi 포스터 출력용)과 동일한 50cm×50cm**다. 버티포트 전체 직경도 3m로 원래 계획 가정과 정확히 일치.

**결론: §4.1 GSD 표는 정정 없이 그대로 유효하다.** fine ArUco 락 가능 고도는 원래 가정대로 **~20m 이하**.

**단, 이번 확인으로 버티포트 구조가 훨씬 상세히 확정됐다(§2/§5.2 참조):**
- 흰색 **채워진** 원형 필드(직경 3m) — 이게 coarse 1차 신호(크고 채워짐, 저해상에서도 강함). 바깥 테두리에 검은 띠, 내부에 검은 V(solid, 실물도 검은색 확인).
- 하기안전구역(빨간 원): **직경 2m, 선굵기 5cm** — 채워진 disc가 아니라 5cm 두께 고리(annulus). 흰 필드가 이미 1차 신호를 맡으므로 이건 coarse 2차 확인/허용오차 경계로 충분 — 색게이팅(HSV빨강)+점군 원피팅으로 검증(§5.2).
- 5cm 선굵기 기준 GSD 가시성: 40m(다운스케일 6.4cm/px)에서는 선폭이 GSD보다 좁아 끊겨 보일 수 있음 — 다만 1차 신호가 흰 필드(면적)로 바뀌었으므로 설계상 치명적이지 않음. 실기체 데이터로 빨간 고리 신뢰 하한고도만 확인하면 됨.
- 검은 띠 바깥 경계 처리(여분 흰색/현수막/정확한 절단)는 미상 — coarse 설계(흰 필드 내부만 봄)에는 영향 없음, §9 2단계에서 확인.

### 4.2 자세(tilt) 오차 — 짐벌이 없다

나디르 하드마운트라 기체 기울기 = 카메라 기울기. 지상오차 = 고도 × tan(θ).

- 40m·5° → **3.5m**. 40m·2° → 1.4m. → 30cm 요구 대비 치명적.
- 대응(모두 필수):
  1. **IMU 자세 de-rotation** — blob 타겟(초록/박스/빨강십자)은 pose가 없어 centroid를 자세로 보정.
  2. **ArUco solvePnP** — 시야각을 내재 보정(버티포트 터미널은 상대적으로 견고).
  3. **근접 호버서만 측정** — 각속도·기울기가 작을 때만 샘플링 (롤링셔터·모션블러도 동시 완화, §6).
  4. **⚠️ 고무 마운트의 역설:** 진동댐핑이 카메라를 IMU와 분리시켜 **IMU 자세 ≠ 실제 카메라 자세** 잔차. 정밀 요구 시 카메라 IMU 또는 단단한 마운트 고려.

### 4.3 측위 한계 — 30cm는 폐루프로만

일반 GPS "픽셀→GPS→그 GPS로 비행"은 1~2m가 하한. **30cm는 카메라가 제어오차를 직접 측정하는 폐루프 비주얼 서보잉**으로만 달성. "착륙할 때만 정확하면 된다"는 요구와 일치: GPS로 근방 접근 → 비전으로 정밀 정렬. 기존 `geo_project.pixel_to_gps`는 이 이유로 폐기.

## 5. 검출 전략

### 5.1 공통 상태머신 (타겟 종류 무관)

```
ACQUIRE(대형 coarse 피처) → CENTER+DESCEND(중심 맞추며 하강)
  → LOCK(fine 피처 확정·검증) → PRECISION SERVO(폐루프) → TERMINAL(AGL/블라인드 하강)
```
- **커밋 게이트:** fine 피처 락·검증(ArUco ID 화이트리스트 / 초록+은색테두리 동시확인) 전엔 최종 착륙 금지. 후보 2개·모호 시 홀드/재상승.
- **중심 맞추기는 고도 불문** — 타겟을 화면 중앙으로 몰면 됨(픽셀오차→0). 고도(라이다 AGL)는 게인 스케일·스로틀컷 타이밍에만.
- **TERMINAL 데드레코닝 (터미널 블라인드니스 대응):** 근접 하강 시 마커가 화각(102°라도)을 이탈해 검출이 끊긴다. 마지막 유효 pose + 라이다 AGL로 **데드레코닝 하강**하되, (a) 최대 블라인드 지속시간·(b) 예상 착륙점 이탈 임계를 두고 초과 시 재상승. "안 보이는데 계속 내려간다"를 금지하는 게 핵심.
- **blob 타겟 스케일 융합 규칙:** ArUco는 solvePnP로 자체 스케일이 나오나, ②초록매트·흰박스·③빨강십자 blob은 pose가 없어 **픽셀 centroid→미터 변환의 스케일이 라이다 AGL이 유일**하다. 규칙: 라이다 유효 시 AGL로 스케일, 라이다 상실 시 (기지 타겟 물리크기↔관측 픽셀크기)로 대체 추정, 둘 불일치 시 plausibility 게이트가 락 거절(§7.5). 어느 소스를 썼는지 `TargetEstimate` 신뢰도·JSONL에 기록.

### 5.2 ① 버티포트 — coarse 3단 계층 확인 캐스케이드 (2026-07-21 확정)

구조: **흰색 채워진 원형 필드(직경 3m)** → 바깥 테두리 **검은 띠** → 내부 **검은 V**(solid) → **빨간 고리**(직경2m·5cm) → 정중앙 **ArUco 50cm×50cm**. 이 층위를 그대로 신뢰도 오름차순 확인 단계로 쓴다:

1. **1차(가장 원거리, ~40m~): 흰 필드 채움 탐지.** 자갈 배경 대비 고대비·큰 면적 → 기존에 이미 있고 테스트된 `ColorFilter(mode="gray")`(명도 기반, 무채색) 재사용 — 신규 개발 최소. 크고 채워진 신호라 저해상에서도 강함. 중심 추정치 산출.
2. **2차(중간 거리): 검은 V 형상 확인.** solid라 저해상에서도 강한 형상 신호 — 흰 필드 내부에 검은 V가 있는지로 다른 밝은 물체(오탐)를 배제.
3. **3차(근거리, coarse 끝~허용오차 경계): 빨간 고리(직경2m·5cm) 확인.** 채워진 disc가 아니라 5cm 두께 고리이므로 면적 blob 방식은 안 맞는다 — **HSV 빨강으로 후보 픽셀만 먼저 게이팅한 뒤, 그 점들에 원 피팅(최소외접원/대수적 원피팅)** 으로 검증(일반 그레이스케일 Hough보다 클러터 오탐 적고 계산도 가벼움). 중심 1m 이내 = 안전권 허용오차 경계로 사용.
- **fine(≤~20m):** 중앙 ArUco 50cm×50cm → **solvePnP 상대 pose + ID(23) 검증**.
- **미상:** 검은 띠 바깥으로 흰색/현수막 여분이 더 있는지, 정확히 띠 경계에서 잘려 자갈과 맞닿는지는 실기체 데이터(§9 2단계)로 확인 — 현재 coarse 설계(흰 필드 내부만 봄)에는 영향 없음.

### 5.3 ② 조난자 구역
- coarse(40~15m): 초록 사각 매트(자갈 위) → HSV 초록 + 사각. 은색 테두리(5cm)는 저고도 확인용. **[2026-07-21] 초록 매트 크기는 비공개 확정(앞으로도 미공개) — 버티포트와 비슷하되 안전마진으로 약간 작게 가정.**
- fine(≤~15m): 중앙 흰 박스(고명도 blob) → **박스 옆** 빈 초록면 착륙.
- **핵심 난제 = 초록 색조 비동일**(§5.5).

### 5.4 ③ 하기구역 (규정 비공개 확정)
- **[2026-07-21 확정] 대회측이 상세 규격을 의도적으로 비공개.** 버티포트와 유사한 크기로 가정 + 안전마진. 소재=바닥 인쇄물, **CMYK 빨강 계열**로 가정(정확한 색값은 획득 후 §5.5 현장 캘리브레이터로 흡수).
- 빨간 십자: HSV 빨강 + 십자/플러스 형상.
- ⚠️ ①의 빨간 원과 ③의 빨간 십자가 둘 다 빨강 → 타겟은 명령이 지정하므로 해당 검출기만 구동. 동시 시야 여부 확인 필요.
- **빨강 혼동 방어:** 구동 중인 검출기는 색만으로 확정하지 않고 **형상 판별**(원형도 vs 십자/플러스 aspect·꼭짓점)로 다른 빨강을 배제한다. 명령이 지정한 타겟과 형상이 불일치하는 빨강 blob은 후보에서 제거하고 **거절 이유를 로깅**(§7.4).

### 5.5 색 항상성 (초록·빨강 검출의 심장)
- **레이어드 HSV** + **현장 색 캘리브레이터**(라이브 ROI 샘플→임계값 자동 설정) — 규정·색이 대회 직전 공개돼도 코드 수정 없이 대응.
- **흰 박스 = 프레임별 화이트밸런스 앵커**(②). 버티포트는 흰 패드/알려진 빨강·검정을 앵커로.
- ±3h 비행시간대·그림자·광택 글레어·과노출 클리핑 대비 → 여러 시간대 실측 + 노출 고정(§6).

### 5.6 ④ 단순 착륙 — **[2026-07-21 확정] GPS + 라이다 하강만**
- 피듀셜이 없어 ①~③의 fine 락·검증 체계 자체가 적용 대상이 아니다. **비전 검출/좌표 개입 없이 GPS + 1D 라이다(AGL)만으로 하강한다.**
- vision 모듈 관점에서 ④는 **개발 범위 밖**(coarse/fine 파이프라인·`TargetEstimate` 발행 대상 아님) — offboard/FC 쪽에서 순수 GPS+라이다 하강 로직으로 처리. `docs/session_status.md`(FC 트랙) 연동 시 이 사실만 전달하면 됨.
- 참고로 검토했던 비전-보조 후보들((a)무채색 사각형 검출기 재활용 / (b)라이다·GPS+비전veto / (c)텍스처·평탄도 스코어링)은 **채택하지 않음** — 순수 GPS+라이다로 결정.

## 7. 변경 내성 & 관측성 아키텍처 (1급 항목)

> **원칙: 변하는 것을 인터페이스 뒤에 격리하고, 모든 실행을 기록·재생 가능하게 하며, 설정으로 주도하고, 구조적으로 로깅한다.**
> 기존 `vision/`의 config-driven 파이프라인 + `VisionState` 계약이 이미 이 방향 — 확장한다.

### 7.1 원칙 — ports & adapters
검출 **코어(검출+기하)는 순수 라이브러리**. 카메라·출력·설정·로깅·시각화·인코더는 전부 어댑터. 코어가 뱉는 건 중립 dataclass `TargetEstimate`(상대 pose + 신뢰도 + 타입 + frame_id + timestamp) 하나.

- **좌표 프레임 계약 — [2026-07-21 잠정 확정]:** 카메라가 아직 최종 고정되지 않은 현시점에서는 **카메라 광학 프레임 기준**으로 출력한다(잠정). **궁극적 목표는 body 기준 기체 정중앙**이 착륙지점 바로 위에 오도록 하는 것이나, 카메라 마운트 확정·de-rotation 캘리브레이션 전까지는 도달하기 어렵고, **필요성이 낮거나 불안정하면 body-center 정렬을 굳이 추진하지 않는다**(광학 프레임 상대 pose로 충분하면 그대로 유지). 카메라 마운트가 물리적으로 확정되는 시점에 재검토.
  - 단위·부호 규약, offboard 정밀착륙 서브상태와 `LANDING_TARGET`이 각각 기대하는 프레임 매핑은 **여전히 미정** — 출력계약 확정(빌드순서 4단계) 전에 정의 필요.
  - 폐루프 게이팅·게인용 **불확실성(공분산 또는 신뢰 반경)** 필드 포함 여부도 여기서 결정 — 미정.

### 7.2 변화 흡수 지도

| 초록 크기/색 | 런타임 config + 현장 색 캘리브레이터 | 슬라이더/ROI |
| 규정/절차 | `TargetSpec` + 상태머신 config | 설정 테이블 |
| CC 명령(타겟 지정·시작 트리거) | `CommandSource` 어댑터 (ROS 토픽/서비스; CC 미구현 동안 mock/CLI) | 어댑터 교체 |

### 7.3 config / 튜닝
- 레이어드: 기본값 → 카메라 프로파일 → 타겟/미션 프로파일 → **런타임 오버라이드(launch 인자/CLI/라이브)**. (FC 규칙 "임시값은 yaml 안 고치고 launch 인자로" 계승.)
- **매직넘버 금지** — 모든 상수는 이름·기본값·설명 있는 param.
- **provenance echo** — 시작 시 해석된 전체 config + **git 커밋 해시** + 사용한 캘리브레이션 id를 로그 헤더에.
- **기능 플래그** — 각 타겟 브랜치·각 완화를 on/off로 현장 이분탐색.

### 7.4 로깅 (터미널 + 파일)
- **이중 싱크 구조적 로깅**: 터미널(사람용, 레벨/색) + 파일(.log). 레벨 DEBUG/INFO/WARN/ERROR.
- **프레임별 기계로그 JSONL** = 블랙박스: {ts, frame_id, alt, attitude, detections[점수·위치], chosen, command, state, latency}. 사람로그와 분리.
- **거절 이유 로깅** (왜 후보를 버렸나) — false-negative 디버깅의 금맥.
- **⚠️ 비차단(non-blocking)**: 로깅/기록은 큐+별도 스레드, bounded, drop-oldest. **제어 루프 핫패스를 막지 않는다**(디스크 I/O가 setpoint를 지연시키면 기체 흔들림).
- **로테이션** (크기/시간).

### 7.5 기록·재생 (최대 디버깅 레버)
- **모든 비행/개발 런에서 원본 프레임 + 텔레메트리를 타임스탬프와 함께 기록** → 책상에서 **동일 파이프라인 오프라인 재생**. 테스트 기체·제한된 비행 환경에서 개발 속도 최대 배수.
- **결정론적 재생**: 코어에 wall-clock/난수 없음 → 같은 입력+config = 같은 출력. `FrameSource`에 `Dir/BagFrameSource`.
- **골든셋 회귀 테스트**: 라벨된 프레임 폴더(고도별·타겟별) 검출 유지 assert. "X 고치다 Y 깨짐" 방지.
- **⚠️ works-in-recording-fails-live**: 비행에 쓸 캡처 설정 그대로 녹화, 재생에 텔레메트리 포함. **plausibility 게이트**(프레임간 점프, 고도 대비 타겟크기, solvePnP거리↔라이다 불일치)로 엉뚱한 락 거절.

### 7.6 세 "화면" + 격리 규칙
하나의 파이프라인이 프레임별 아티팩트(`raw`→`compute`→`mask`→`overlay`, 동일 frame_id/ts)를 내고, 독립 토글 탭을 단다:

| | 무엇을 | 언제 | 성격 |
|---|---|---|---|
| **#1 telemetry_video** | `raw`/`overlay`, 안전마진 내 최대품질 | 항상 | 기본 다운링크 |
| **#2 compute_tap** | `compute`/`mask`를 **재가공 없이 그대로** | dev 토글 | 패리티 검증(핵심) |
| **#3 presentation** | **지상국**에서 표시용 후처리 | 대회 토글 | 지상 출력 전용 |

- **#3 정직 재정의**: 목표는 "저대역 링크 탓에 멀쩡한 시스템이 못나 보이는 것"을 지상국 버퍼링·프레임보간·깔끔한 오버레이로 **바로잡는 것**(정당). "실제 버벅임을 노이즈·합성으로 심사위원에게 속이는 것"은 **재고** — 자기기만(진단신호 은폐)·규정/신뢰 리스크. 표시 fps를 링크 fps와 분리하면 정직하게 "여유로워" 보인다. `PRESENTATION` 워터마크 = 정직한 방식.
- **격리 규칙(하드):** #3 화장 레이어는 지상 출력 전용. `compute`·JSONL·녹화/재생·plausibility·운영자 결정뷰에 **절대 닿지 않는다.** 운영자 안전판단은 저지연 정직뷰.
- **⚠️ headless-safe**: 드론엔 디스플레이 없음 → `cv2.imshow` 무조건 호출 금지(플래그 뒤로). **기존 `main.py`가 지금 무조건 imshow → Pi에서 크래시**(§12).

### 7.7 FPV 영상 토폴로지 + 인코더 어댑터 + USB2 제약
- **Pi5는 HW 인코더가 없다** → H.264 인코딩이 소프트웨어(CPU). 예산을 먹는 건 **전송(Ruby/WFB-NG)이 아니라 인코딩**이다. (1080p30 SW 인코딩 ≈ 1코어의 60% / 4코어 중.)
- **정량:** raw 영상은 크다(1080p30 YUV420 ≈ 746 Mbps). **USB2.0 실측 ~300 Mbps** → 풀해상도 raw를 Pi5→Pi4로 넘겨 인코딩(안)은 불가. VGA급이 한계.
- **두 토폴로지:**
  - (X) Pi5 카메라 영상 → Pi4 인코딩: USB2 raw 대역폭 벽 → 함정.
  - (Y) **Pi4 = 자체 카메라 에어유닛**: USB2엔 메타데이터만 → Pi5 CPU 0. 권장.
- **권장 구성:** #1 기본영상은 Pi4(또는 경량 OpenIPC 캠)가 자체 카메라로 무료 운반. **Pi5는 검출 메타데이터(숫자)만** USB2 이더넷-가젯으로 → **지상국이 오버레이 합성**. dev용 #2 패리티 미러는 **다운스케일(VGA급)** 이라 USB2에 맞음.
- **⚠️ 정합 caveat:** (Y)는 FPV 카메라 시점이 달라 Pi5 검출 bbox가 FPV 영상과 **픽셀정합 안 됨**(지상 오버레이는 근사). 픽셀정합 필요 시에만 Pi5가 자기 프레임을 다운스케일 인코딩(비용 발생).
- **부수:** Pi4 도입은 무게·전력·부팅·고장점·두 보드 시간동기(§7.8) 추가. USB 버스 경합 주의(FPV WiFi 어댑터는 Pi5 USB3로). **인코더는 스왑 어댑터**(`Pi5SoftwareEncoder`/`Pi4OffloadEncoder`/`AirUnitMetadataOnly`)로 두어 Pi4 확정 전이든 후든 코어 불변.
- **[2026-07-21 확정 방침] Pi4 채택은 "일단 Pi5 SW 인코딩으로 해보고, 문제가 지대하면 그때 도입"** — 두 가지가 함께 필요:
  1. **Pi4 전환 권고 시스템:** Pi5 SW 인코딩 운용 중 CPU 점유율·인코딩 지연·열 스로틀링(§11 블라인드스팟)을 계측해 임계값 초과 시 "Pi4 전환 권고"를 로그/알림으로 낸다. 구체 임계값(예: 인코딩이 검출 루프 예산을 잠식하는 CPU%, 지속 스로틀 온도)은 §7.4 구조적 로깅에 얹어 §9 2단계(실기체 데이터 수집) 때 실측 기준선을 잡는다.
  2. **구조 선채택:** 위 `EncoderSink` 스왑 어댑터 패턴이 이미 이 요구를 충족한다 — Pi4 채택 여부와 무관하게 코어가 불변이도록 지금부터 어댑터 경계 뒤에 인코더를 둔다(신규 구현 불필요, 기존 설계 유지가 곧 답).

### 7.8 시간 동기
- 프레임 SensorTimestamp(Pi 클록) ↔ MAVROS 자세 시간의 **오프셋 캘리브레이션** 필요 (de-rotation 정확도 직결). Pi4 도입 시 **두 SBC 간 클록 동기**로 확장.

### 7.9 개발단계 디버깅 워크플로 (dev feedback loop)

> §7.4~7.6은 관측성 *아키텍처*를 정의한다. 이 절은 그것을 **개발자가 실제로 영상·로그를 보는 구체 도구·전송경로·명령**으로 못박는다. 드론이 **헤드리스**(디스플레이 없음)로 돌기 때문에, "작동영상"과 "로그"가 개발자 책상까지 도달하는 경로가 1급 요건이다.

**두 디버깅 모드**
- **오프라인 재생(desk) = 주력.** 벤치/비행 런에서 raw 프레임+텔레메트리를 녹화 → 책상에서 **동일 파이프라인**으로 재생. 반복 가능·결정론·빠름 → dev 디버깅의 대부분이 여기서. (제한된 비행환경에서 개발속도 최대 레버, §7.5.)
- **라이브(on-drone) = 보조.** 파이프라인이 실시간으로 도는 걸 확인. Pi 헤드리스라 랩탑으로 스트림.

**작동영상 피드백 3경로**

| 경로 | 메커니즘 | 용도 |
|---|---|---|
| (a) 재생 오버레이 뷰어 | `Dir/BagFrameSource` → overlay → window/mp4 | **데스크 주력** |
| (b) 라이브 저해상 스트림 | `compute_tap`(VGA급) → MJPEG-over-HTTP **또는** ROS2 `image_transport`(Foxglove/rqt_image_view) | 현장 랩탑 실시간 |
| (c) mp4 상시 덤프 | overlay를 파일로 항상 기록 | 비행 후 리뷰 |

**로그 3종** (모두 §7.4): 사람 로그(터미널 색·레벨 + `.log` 파일) / **프레임별 JSONL 블랙박스**(기계) / **거절 이유 로그**.

- **JSONL은 쌓기만 하면 안 보인다 → 뷰어가 필수.** 시간축으로 검출점수·latency·state·alt를 플롯(Foxglove 레이아웃 또는 소형 스크립트). **프레임 ↔ JSONL 행 ↔ 오버레이**를 같은 frame_id로 동기해 나란히 본다.
- **인터랙티브 튜닝 루프:** 재생 화면 위 OpenCV trackbar 또는 config hot-reload로 HSV 임계값을 즉시 조정 — 색 항상성 난제(§5.5)의 tune→see 루프를 초 단위로.
- **frame-step + partial:** 기존 `partial(N)`(vision/CLAUDE.md) + 각 단계 `mask`/`meta` 덤프를 재생 뷰어에 연결 → 다단 CV 파이프라인을 단계별로 격리 관찰.

**비침습 전제:** dev 계측이 제어루프를 지연시키면 안 된다(§7.4 비차단, Heisenbug 회피). 재생은 결정론(코어에 wall-clock/난수 없음).

**지금 당장 할 일 (빌드순서 3단계의 구체 착수 목록)**
1. `main.py` **headless-safe**: 무조건 `cv2.imshow` 제거 → `--display {none|window|stream|file}` (none=드론 기본). *(현재 크래시 원인, §12 즉시수정)*
2. **이중싱크 로거** + provenance 헤더(해석된 config + git 커밋 해시 + 캘리브 id).
3. **프레임별 JSONL 블랙박스**(비차단 큐+스레드, bounded/drop-oldest, 로테이션) + **거절 이유**.
4. `FrameSource` 어댑터(Live/`Dir`/`Bag`) + **재생 CLI 엔트리**(예: `python -m vision.replay <녹화폴더|bag> --preset ...`).
5. **라이브 스트림 어댑터**(`compute_tap` VGA → MJPEG/ROS image) — 랩탑에서 실시간 관찰.
6. **JSONL 뷰어/플롯** 최소본(시간축 점수·latency·state).
7. **골든셋 폴더 스캐폴드**(라벨 프레임, 고도·타겟별) + 재생 회귀 assert.

## 8. 통합 (fc_ros offboard)

- **독립 ROS2 노드**가 `TargetEstimate`(기체 기준 상대 pose)를 publish → **offboard_node의 정밀착륙 서브상태**가 소비해 폐루프 유도.
- 출력을 **상대 pose**로 두면 (a) 자체 서보 컨트롤러, (b) `LANDING_TARGET`(MAVLink) 네이티브 precision-land 양쪽에 그대로 사용 → **정밀 미달 시 네이티브로 피벗**.
- **페일세이프 계약:** 비전 노드 크래시/검출 상실/브라운아웃 → offboard가 홀드·재상승(기존 OVERRIDE 계열 재사용). "추측 후 커밋" 금지.
- 도메인 의존은 루트 `CLAUDE.md`에 기록됨 (`vision → fc_ros`).

7. **offboard 정밀착륙 서브상태 연결**
8. **폐루프 튜닝 → 30cm 검증** → 미달 시 GS 카메라/네이티브 precision 피벗

## 12. 기존 `vision/` 틀 처리 방침

기존 틀은 "무채색 사각형 윤곽선 검출기"(color→edge→morphology→rect→fusion)로, **정밀 fiducial 시스템이 아니다.** 그러나 폐기가 아니라 재편한다:

- **재활용:** config-driven 파이프라인 골격 + `VisionState` 계약 + preset + `partial()` 디버그. **② 조난자 구역 색 검출 파이프라인**(`ColorFilter(color)` + `RectDetector`)은 그대로 유효.
- **신규:** `cv2.aruco` + `solvePnP` 모듈(bbox엔 pose 없음), `FrameSource`/`TargetSink`/`EncoderSink` 어댑터, 구조적 로깅+JSONL, 기록/재생, 현장 색 캘리브레이터, config 검증+provenance, schema 버전 출력.
- **폐기:** `geo_project.pixel_to_gps` (GPS 절대좌표 방식 → 상대 pose 폐루프로 대체).
- **즉시 수정:** `main.py`의 무조건 `cv2.imshow` → headless-safe (Pi 크래시 방지).
